# plan9 評測輸出

`plan9.md` 階段 A 的評測結果放在這裡。**這裡放的是證據，不是計畫書**——評測一旦跑完就
必須能從 repository 重算，否則它只是某個終端機上的一次輸出。

## 為什麼這個目錄要單獨加一行 .gitignore

`.gitignore` 第 10 行的 `plan*` 會匹配**任何以 `plan` 開頭的路徑元件**，所以
`eval/plan9/` 原本整個被忽略，而且是靜默的：檔案照樣寫得進去，`git status` 只是永遠
不會提到它們。`!eval/plan9/` 一行把它救回來，`plan*.md` 仍維持忽略。

這裡**不需要** `data/` 那段的三行寫法。那裡必須先取消排除父目錄，是因為 git 不會
descend 進被排除的父目錄；`eval/` 本身沒有被排除，所以指名那一個目錄就夠了。

## 目錄內容

| 檔案 | 入庫 | 內容 |
| --- | --- | --- |
| `README.md` | 是 | 本檔 |
| `<批次>-summary.json` | 是 | 每個選項的席次、平均分、平均餘格、標準誤 |
| `<批次>-games.json.gz` | 是 | 逐局明細，**gzip 壓縮** |
| `<學生>-pair.json` | 是 | 一個學生 0k 對 `hc_1000` 的成對量測:摘要 + 逐局得分/餘格/名次 |

未壓縮的逐局明細約 245 bytes/局（實測自
`data/match/seed20260928-g500-poolno_imitation_hc_1000.json`：500 局 122,411 bytes）。
`gzip -9` 把它壓到 **6.7%**，即約 16 bytes/局——N=2000 的一批從 0.47 MB 降到 0.03 MB。
壓縮後進版控，這樣成對統計的原始資料仍在 repo 裡，不必靠「當初那台機器還在」才能重算。

## 產出方式

逐局明細由 `match.py --out` 寫出，之後另行 gzip：

```bash
.venv-rl/bin/python match.py --pool no_imitation --games 2000 \
    --seed 20261005 --paired-rng --subject <KEY> \
    --mode argmax --out eval/plan9/<批次>-games.json
gzip -9 eval/plan9/<批次>-games.json      # -> <批次>-games.json.gz
```

`--subject` 尚未實作（設計待確認）。`--out` 一定要帶：`match.py` 的預設輸出目錄是
`data/match/`，而 `data/` 受測試的檔案守衛看管。

## 每個批次必須記錄的東西

摘要檔與逐局檔都要帶上以下欄位，缺一就不算完整證據：

- **`rng_mode`**：`match.py` 自己會寫（`paired-v1` 或 `legacy-single-stream`）。
  成對結果與排行榜結果的抽籤方式不同，兩者不可混合平均。
- **`--seed`**、**`--pool`** 原始字串與展開結果、**`--mode`**（argmax / softmax）。
- **母體定義**：哪些局被納入統計、被排除的局有幾局、排除理由。
  （固定 subject 席位的模式下母體是全部有效局；在場率不是 100% 的舊設計才需要這一段。）
- **有效局數**與**排定局數**。
- 對照物名稱、以及對照物是否也出現在對手席。

## 探索性分析(**不屬於上述四個,不得當成通過依據**)

### (a) 局內四席是否同向移動

四席得分恆和為 10,所以「得分」的原始相關必然為負,是恆等式而非經驗發現;改用
「相對該局均值的離差」計算,結果**恆為 −1.000**(離差總和為零),同樣不含資訊。
因此以**餘格**為指標:

| mode | subject | 與三個對手席餘格的相關 | 對手席彼此餘格的相關 |
| --- | --- | --- | --- |
| argmax | `rl_h1000_20k` | −0.159 / −0.094 / −0.161 | −0.177 |
| argmax | `hc_1000` | −0.169 / −0.080 / −0.149 | −0.161 |
| argmax | `hunter` | −0.166 / −0.144 / −0.194 | — |

**全部為負。**若存在「這一局本來就好打/難打」的共同因素,預期為正;觀察到的負相關
與「四席競爭同一批格子、名次由餘格決定」一致。**所以這個資料並不支持「共同命運」
假說,配對只省下約 8–10% 標準誤的原因仍未定論。**

> 假說(未經證實):差異主要殘留在局內後續的對手行為漂移——分流讓 setup 成對,但被測
> 模型落子後局面即分歧,對手的後續選擇必然不同。此假說與上表結果**不一致**,
> 僅作為待查線索保留。

### (b) argmax 相對 softmax 的增益,及其差的差

`--mode` 不進入抽籤,所以四個格子共用同一個 setup,這一組也成對。

| 指標 | 模型 | argmax − softmax | 成對 SE | t |
| --- | --- | --- | --- | --- |
| 得分 | `rl_h1000_20k` | +0.5025 | 0.0282 | +17.82 |
| 得分 | `hc_1000` | +0.2445 | 0.0276 | +8.87 |
| 得分 | **差的差 (rl − hc)** | **+0.2580** | **0.0392** | **+6.59** |
| 餘格 | `rl_h1000_20k` | −4.9040 | 0.2226 | −22.03 |

## 步驟 4 的事前固定規則(2026-10-06 決定,先於任何學生結果)

本節在 o / b / i 三個學生的任何結果產出**之前**寫定。看到結果之後不得修改本節;
若需要改,必須另開一節並註明是事後修訂,以及修訂的理由。

1. **驗收以 argmax 為準。**步驟 4 的報告頁首必須註明:
   「通過標準僅限 argmax;softmax 下 h 版對 `hc_1000` t = −0.44,未作為標準」。

2. **不做組 B。**報告不得宣稱任何模型「在更難的對手上成立」。組 A 的池是
   `no_imitation`(七個人格),與訓練條件相同;沒有更難對手的證據,就不寫這句話。

3. **起跑規模 500 局。**種子 `20261005`,指令形式
   `--paired-rng --subject <key> --mode argmax --pool no_imitation --gzip`。
   - 某個比較的 **|t| > 2** → 記錄為**達標**。
   - **|t| ≤ 2** → 記錄為「**500 局下無法判定**」。**這不是失敗**,是這個規模下
     還分不出來。
   - 對 |t| ≤ 2 的比較,**可補跑到 2000 局一次,不再加**。補跑沿用同一種子
     `20261005` 與同一個 `--games 2000`——因此前 500 局與原批次逐局相同,不是
     另換種子的重跑。
     **註(階段 3 之後):** 這裡的「原批次」是**本協議自己**的 500 局批次 ——
     500 局與補跑的 2000 局都在階段 3 之後跑,池同為 key 排序,所以這句仍然成立。
     但**與階段 3 之前的 0.5b 批次不再前綴相容**:那六批的池是註冊表順序
     (`wolf, chess, fox, intruder, optimizer, builder, hunter`),而現在
     `no_imitation` 展開成 key 排序,同一個種子會抽出不同的對手。要跟那六批對齊

4. **規則在看到任何學生結果之前固定,不得事後調整。**

### 為什麼是兩段式而不是一次 2000 局

0.5b 對 h 版跑的是 2000 局(argmax 與 softmax 各三批)。學生有三個、每個要對兩個
對照物,一次 2000 局乘上所有格子太貴。而 0.5b 的四個預先固定比較已經把 argmax 的
t 值落在 9.51(達標)與 −0.44(無法判定)兩端,所以 500 局的第一段足以把這兩種情況
分開,兩段式不會把真差異藏起來。

### 這個檔案為什麼是規則的落腳處

`plan9.md` 本身被 `.gitignore` 的 `plan*` 規則忽略(與 `plan2.md` … `plan8.md`、
`plan.md` 相同——只有 `plan.md` 是被追蹤的),所以規則寫在 plan 裡不會進版控,也就
沒有辦法證明它是「看到結果之前」定的。`eval/plan9/` 是被追蹤的,所以規則寫在這裡。

### `records.json` 中 `rl_h1000_20k` 的 `commit` 欄位為 `null`

`commit` 欄位的語意是**「訓練出這些權重的程式碼版本」**。`rl_h1000_20k` 的值是
`null`,不是 `82bfadf`、也不是 `0119360`:

- 訓練(2026-10-05 07:34–08:28)當下**沒有任何程式碼記錄自己的 commit**。checkpoint 的
  blob、`rounds.jsonl`、`eval.jsonl` 都沒有 commit 欄位。
- git 歷史可把該時段夾到唯一的 `82bfadf`(時段內 0 個 commit;前一個 10-05 01:12,
  下一個 `1f91b04` 10-05 08:56)。**但這是推論**:沒有任何東西證明當時工作樹乾淨,
  而 reflog 只記 HEAD 移動、不記工作樹內容。
- 本專案自己的標準(`rl/collect.py` 的 `code_hash()` 註解)是「工作樹有未提交變更時,
  單靠 commit 不能識別這份資料」——該函式同時記 `dirty`。`rl/rl_train.py` 沒有。

所以填 `null`,並記錄原因。修法在訓練端:比照 `code_hash()` 把 commit 與 dirty 寫進
checkpoint,留給之後動訓練程式碼的提交。

## 事後更正:模仿資料的種子基底是 6,000,000,不是 1,000,000

**這一節是事後更正,寫於看見任何學生結果之前。**

plan9 步驟 0 的報告裡,我把 `rl/collect.py` 的預設值 `TRAIN_SEED_BASE = 1_000_000` /
`VALID_SEED_BASE = 2_000_000` 當成 `data/hc1` 的種子基底寫進報告。**那是錯的。**程式碼
裡的常數已經在那次收集之後被改過,讀程式碼讀不出當時用的是什麼。

`data/hc1/manifest.json` 的分片清單記下了當時實際使用的範圍:

```
train  : hb1_train_6000000_6000508.npz  ..  hb1_train_6029378_….npz   (60 個分片)
valid  : hb1_valid_6100000_6100128.npz  ..  hb1_valid_6101545_….npz   (12 個分片)
```

**TRAIN base = 6,000,000,VALID base = 6,100,000。**

**為什麼這個更正重要。**`data/hc1` → `hc_1000` → `rl_h1000_20k` 是同一條鏈。步驟 3 規定
o / b / i 的 RL 要「與 `rl_h1000_20k` 逐項相同」,而 h 版的模仿資料用的是 6,000,000
基底。若學生用 1,000,000,則「逐項相同」在種子這一項上不成立,而症狀只會出現在訓練
曲線上,沒有任何東西指向原因。

### 新範圍與其他範圍的重疊檢查

| 範圍 | 區間 | 與新範圍重疊? |
| --- | --- | --- |
| RL 訓練(`rl_train.py`) | 7,000,000 – 7,019,999 | 否 |
| RL 輪中評測 | 7,100,000 – 7,100,999 | 否 |
| `bench_engine` | 0 – 199 | 否 |
| `tools_benchmark` | 20,240,101 – 20,240,197 | 否 |
| 0.5b 評測種子 `20261005` | 見下 | 否 |

0.5b 的 `--seed 20261005` 是 `match.py` 單一 master `random.Random` 的種子,不產生
6,000,000–6,101,999 的整數,也不消耗任何 `collect.py` 的種子,所以與分片區間不可能重疊。

**但新範圍落在 `RESERVED_RANGES` 的兩個區塊之內**,這一點必須講清楚,因為它看起來像
衝突而其實是預留給同一用途:

```
('H-B1/H-C1 imitation train', 6000000, 6029378)
('H-B1/H-C1 imitation valid', 6100000, 6101545)
```

這兩個區塊是為了標記「模仿資料的種子範圍」而保留的(plan8 B0 建立),**保留給的正是
這個用途**。新的學生資料用它們,是使用預留而不是侵犯預留。

要注意兩個 `check_seed_ranges` 的管轄範圍不同:

- `rl/collect.py` 的 `check_seed_ranges` **只看 bench 兩個範圍**,所以 6,000,000 會被接受。
- `rl/paired3.py` 的 `reject_reserved_seeds` 會**拒絕** 6,000,000(它落在預留區塊內),
  但那是給 RL rollout 用的護欄,`collect.py` 不呼叫它。

### 一個尚未解決的差異:資料規模

`data/hc1` 涵蓋約 **29,505 train 局 + 1,420 valid 局**(`total_games` 30,925)。本階段的
學生資料是 **2,000 + 200 局**,規模約為其 1/15。`hc_1000` 是從 29k 局蒸餾的,學生的 0k
版會從 2.2k 局蒸餾——**這是 0k 起點之間的實在不對稱**,寫報告時必須說明,不能當成
「學生的 0k 版與 `hc_1000` 等價」。

## `teacher_equals_shortlist_first_share` 恆為 1.0:它沒有區分力

步驟 2b 比較了 hunter(`data/hc1`)與 optimizer(試跑)的這個指標,兩者都是 **1.000000**。
**但這不是「兩者性質相近」的證據,而是恆等式。**

四個老師全部是規則型人格,而且都不抽籤:

```
hunter      HunterBrain       mistake_rate=0.00  uses_lookahead=False
optimizer   OptimizerBrain    mistake_rate=0.00  uses_lookahead=False
builder     BuilderBrain      mistake_rate=0.00  uses_lookahead=False
intruder    IntruderBrain     mistake_rate=0.00  uses_lookahead=False
```

`mistake_rate = 0` 且不抽籤,`choose_move` 恆取 (rescored) shortlist 的第一名,而
`teacher_move` 記錄的就是那個 action。**所以對這四個老師,這個指標必然是 1.0。**

hunter 的值是**唯讀重算**出來的:`data/hc1` 從未存過 stats,遍歷 72 個分片照
`summarise()` 的算法重算,讀到的總列數 1,191,605 與 manifest 的 `total_samples`
完全相同,確認讀齊。未跑任何新局。

### 真正可觀察的差異:shortlist 長度——這是步驟 4 的混雜因素

| | hunter(`data/hc1`) | optimizer(試跑) |
| --- | --- | --- |
| 樣本數 | 1,191,605 | 895 |
| shortlist 長度 mean | **13.62** | **19.64** |
| shortlist 長度 max | 34 | 37 |
| `samples_with_empty_shortlist` | 0 | 0 |

optimizer 的標籤空間比 hunter 大約 **44%**。**這是步驟 4 必須記錄的混雜因素**:若某個
學生在步驟 4 的分數較低,原因可能是它的標籤空間較難,而不是模型較弱。步驟 4 的報告在
比較三個學生之前,必須先看各自資料的 shortlist 長度分佈,否則會把資料難度讀成模型差異。

注意 hunter 是 29k 局、optimizer 試跑只有 895 個樣本,這個量級差本身也會影響分佈估計
的穩定性;學生正式資料(2,200 局)會比試跑可靠,但仍小於 hc1 一個數量級。

`data/hc2/run.json` 的 val 曲線也沒有支持它:val 在 10,000 步內單調下降

## 0k 版的停損規則(2026-10-06 定案,寫於模仿訓練開始之前)

任一條觸發即**停下回報**,不自行調整步數或資料。

| 規則 | 門檻 | 量測方式 |
| --- | --- | --- |
| **過弱** | argmax 平均分 **≥ 2.93** | 200 局、種子 6,100,000–6,100,199、同上表的抽法 |
| **過尖** | argmax 平均熵 **≥ 1.281** nats、softmax **≥ 1.245** nats | 同一批局、同一次運行 |
| **過擬合** | val 持續回升,**或** train/val 間距 **> 0.063** | 訓練本身的 val 曲線 |

> **【註記,2026-10-06】上表第三列的 0.063 間距門檻已廢止**——廢止於看到
> `imit_o1000` 的訓練曲線**之後**,理由與證據見下一節
> 「事後修訂:0.063 廢止」。**原文一字未刪**,第一、二列照舊有效。

### 過弱:2.93 的依據

`hc_1000` 的 argmax 平均分是 3.125,本次量測的**單次分數標準誤 0.0665**。0.20 的餘裕
**約等於 2 個差值標準誤**:

```
√2 × 0.0665 ≈ 0.094     0.20 / 0.094 ≈ 2.13 個差值標準誤
```

**不是「3 倍單次標準誤」**——0.20 / 0.0665 ≈ 3.01 是單次的算法,而門檻比較的是兩個
平均值的差,差值的標準誤是 √2 × 單次標準誤。0k 評測後必須回報**差值本身與它的標準誤**,
讓這個門檻的實際觸發情形可核對。

### 過尖:1.281 / 1.245 的依據,以及它偵測不到什麼

門檻是 `hc_1000` 熵的 **80%**(1.6016 × 0.8 = 1.281;1.5564 × 0.8 = 1.245)。

**這是判斷值,沒有證據支持這個比例。**選 80% 的理由是動機層次的:0k 的定位是「策略多
隨機」,若它比 `hc_1000` **還尖** 20%,就與定位相反,而且 0k 的隨機性正是 RL 探索的起點,
太尖的起點會讓 RL 沒有東西可探索。

**門檻離雜訊約 19 個標準誤**(0.20 × 1.6016 = 0.32 nats ÷ 均值標準誤 0.0167 ≈ 19)。
**這個餘裕太大,只能偵測「大幅變尖」,偵測不到「輕微變尖」。**換句話說:若 0k 只尖了
10%,這個規則不會響。它是下限保護,不是細粒度的診斷。

用**比例**而不是絕對值,是因為熵的絕對大小取決於每個局面的合法著數量,而不同老師的
資料其合法著分佈不同(hunter 平均 shortlist 13.62 vs optimizer 19.46)。比例可以吸收
這個差異,絕對值會把資料本身的難度誤判成「過尖」。

### 比例只**部分**吸收合法著數差異——門檻不改,僅註明

上面這段說「比例可以吸收這個差異」,要加上一個限制:**只能吸收一部分。**

`1.281` 這個數是**以 `hc_1000` 在 hunter 資料上的實測為基準**推出來的。一個學生模型
的熵是在**它自己的資料**對應到的局面上量的,兩個分母不是同一批局面:

| 老師 | 平均 shortlist | 相對 hunter |
| --- | --- | --- |
| hunter(`hc_1000` 的基準) | 13.62 | 1.00× |
| optimizer | 19.46 | 1.43× |
| intruder | 25.53 | 1.87× |
| **builder** | **30.39** | **2.23×** |

合法著較多的局面,熵的**上限也較高**。相對於「該模型在該批局面上自己的熵上限」,
固定 `hc_1000` 的 80% 對合法著多的資料**偏鬆**——一個在 builder 資料上變尖的模型,
其熵可能仍高於 1.281,因此這個門檻**對 builder 的偵測力較弱**。

**門檻維持 1.281 / 1.245 不改。**此處只註明:它是下限保護,對三個學生的偵測力不等,
比較三個學生的觸發情形時必須把這一點一併讀進去。

### 過擬合:0.063,以及它的已知限制

> **【註記,2026-10-06】本節的 0.063 已廢止,理由與證據見緊接的下一節。**
> 保留原文,是因為它證明了這條規則**寫定於訓練開始之前**(`db25e03`),以及它當時
> 自以為知道的東西。廢止的部分只有門檻本身,「規則在看到結果之前固定」這條不變。

`0.063 = 3 × 0.021`,而 `0.021` 是 `hc1` 在 **20,000 列驗證集**上觀察到的 train/val 間距
(`data/hc2/run.json` 的 `validation_rows = 20000`)。學生的驗證集只有約 **7,100 列**
(200 局 × 35.6),約 2.8 倍小,驗證雜訊因此約多 √(20000/7100) ≈ **1.68 倍**,
**固定 0.063 在較小的驗證集上誤觸的機率較高**。

**維持 0.063,不調整。**理由:誤觸的代價只是停下回報(不會產生錯誤結果),而調整的
收益不足以讓規則的寫定延後到資料產出之後——那會違反「規則在訓練前寫定」的要求。
若真的誤觸,按規則停下回報即可。

## 事後修訂:0.063 間距門檻廢止,過擬合改為只看 val 曲線(2026-10-06)

**這一節是事後修訂,寫於 `rl_o1000_0k` 的訓練曲線被讀到之後。**上一節的原文與
門檻表一字未刪,只加了註記;本節記錄時間線、廢止的理由與證據、取代它的規則,以及
把新規則回頭套用到 `imit_o1000` 的結果。

### 時間線

| 時點 | 事件 |
| --- | --- |
| 模仿訓練開始之前 | 三條停損門檻寫定(`db25e03`),第三條是「val 持續回升,**或** train/val 間距 > 0.063」 |
| 訓練完成、曲線讀到之後 | 間距 0.3652 觸發第三條,按規則停下回報 |

「規則在看到任何學生結果之前固定」這條要求仍然成立——0.063 確實是在訓練前寫定的。
廢止的原因不是它被事後討價還價,而是它**從一開始就校準錯了**,只是錯法要等第一條曲線
才看得見。

### 廢止的理由與證據:hc2 自己的十個檢查點

`0.063 = 3 × 0.021`,而 `0.021` 取自 hc2 **最後一個**檢查點(step 10,000)的間距。
把十個檢查點全部列出,間距定義為 `val_loss − train_loss`:

| step | train_loss | val_loss | val − train | > 0.063? |
| --- | --- | --- | --- | --- |
| 1,000 | 1.258785 | 1.381272 | **+0.122487** | **是** |
| 2,000 | 1.352593 | 1.342822 | −0.009770 | 否 |
| 3,000 | 1.203596 | 1.189855 | −0.013741 | 否 |
| 4,000 | 1.110979 | 1.154465 | +0.043486 | 否 |
| 5,000 | 1.038074 | 1.119043 | **+0.080969** | **是** |
| 6,000 | 0.836716 | 1.067225 | **+0.230509** | **是** |
| 7,000 | 1.072299 | 1.032928 | −0.039372 | 否 |
| 8,000 | 1.023038 | 0.999982 | −0.023056 | 否 |
| 9,000 | 0.868976 | 0.981923 | **+0.112947** | **是** |
| 10,000 | 0.955842 | 0.976768 | +0.020927 | 否 |

**10 個檢查點裡 4 個超過 0.063**,其中包括與 0k 同視界的 step 1,000
(+0.122487,是門檻的 1.94 倍)。而 hc2 在那之後 val 一路降到 0.9768。沒有任何人會把
hc2 叫做過擬合,可它有 4/10 的檢查點落在自己規則的「過擬合」區間。

**所以錯在校準,不在方向。**原因與算式的性質有關:`train_loss` 是**剛剛訓練完的那一個
批次**(256 列)的損失,`val_loss` 是驗證集的平均,兩者的雜訊量級不同,而規則拿兩者相減
的絕對大小去比一個固定門檻。當時推 `0.063 = 3 × 0.021` 時只看了最後那一點,沒有回頭
逐點檢查——這就是「校準錯誤」的全部含義。

### 取代它的規則:只看 val loss

| 規則 | 門檻 | 量測方式 |
| --- | --- | --- |
| **過擬合** | val loss 自其**最低點**起上升 **> 0.05**,且**連續兩個檢查點**都高於「最低點 + 0.05」 | 訓練本身的 val 曲線 |

- **只看 val,不看 train。** train loss 不進這條規則。
- **0.05 是判斷值,沒有證據支持這個數字**,與過尖門檻的 80% 屬同一類:它是動機層次的
  選擇,不是從任何分佈推出來的。
- **「兩個連續檢查點」是為了排除單點抖動。**單一次回升不足以說明任何事,證據就是
  `imit_o1000` 自己的 900→1000(見下)。
- 這條規則取代上表第三列,**回頭套用到 `imit_o1000`**,並對後續每一個學生的訓練曲線
  適用。

### 回頭套用到 `imit_o1000`(事後套用,結果如實記錄)

## 規模決定:維持 2,000 局(2026-10-06 決定)

| 選項 | 決定 |

### 已接受的限制:h 與 o/b/i 的 0k 資料量差約 14.3 倍

| | train 局數 | train 列數 |
| --- | --- | --- |
| `hc1`(→ `hc_1000` 的 0k) | 29,505 | 1,132,160 |
| optimizer(→ `rl_o1000_0k`) | 2,000 | 78,984 |
| **倍數** | 14.8× | **14.3×** |

**這是接受的限制,不是待修的缺陷。**0k 只是 RL 的起點,RL 隨後會在 20,000 局裡把它
改寫一遍;把 0k 的模仿品質做高對這個用途沒有邊際收益。

### 兩項推論約束

1. **h 與 o/b/i 的 0k 版差距,不得歸因於老師風格。**兩件事同時成立,而且**兩者皆為混雜
   因素,相對大小未知**:

   | 混雜因素 | 實測 |
   | --- | --- |
   | **資料量** | 14.3 倍(1,132,160 vs 78,984 列) |
   | **老師風格** | shortlist 長度相對 hunter:**optimizer +43%、intruder +87%、builder +123%** |

   先前只列了 optimizer 的 +43%,是取樣錯誤——完整實測顯示三個老師的差異大得多,
   builder 的標籤空間是 hunter 的 **2.2 倍**。

   **不得宣稱哪一個「蓋過」哪一個。**14.3 倍是**列數**的比值,123% 是 **shortlist 長度**
   的比值,兩者**量綱不同**,沒有共同尺度可以相除,誰的效應較大在沒有控制任何一項之前
   是未知的。在沒有控制資料量之前,任何「o 的老師較弱」的說法都不成立;在沒有控制
   shortlist 長度之前,同樣不成立。
2. **步驟 4 的主標準是「各學生對自己 0k 的成對差距」**,而不是「學生 vs h 版」。
   前者在同一份資料、同一條鏈上成對,後者混入上面 14.3 倍的資料量差。

### 階段 3 之後:用 literal 重現

`--pool-order literal` 照 `--pool` 給的原樣使用 —— 不排序、不去重、不看 `enabled`,
連 `--subject` 的拼法都不正規化。它**只為重現歷史證據存在**,日常評測一律用預設的
`sorted`。preset 名稱不得與 literal 併用(preset 的順序就是註冊表的順序,正是
literal 假定不存在的東西),所以池必須寫成明確名單。

批次檔的 `pool` 欄記的就是這七個、這個順序:

| 欄 | 值 |
| --- | --- |
| `--pool` | `wolf,chess,fox,intruder,optimizer,builder,hunter` |
| `--pool-order` | `literal` |
| `--games` | `2000` |
| `--seed` | `20261005` |
| `--paired-rng` | 開 |
| `--subject` | `hc_1000`(批次檔裡的拼法,literal 不會改寫) |
| `--mode` | `argmax` |

```bash
.venv-rl/bin/python match.py \
    --pool wolf,chess,fox,intruder,optimizer,builder,hunter \
    --pool-order literal \
    --games 2000 --seed 20261005 --paired-rng --subject hc_1000 \
    --mode argmax --gzip --out /tmp/kilo/rerun_hc1000.json
```

**舊批次的池順序是什麼。** `pool_order` 這個欄是階段 3 才加的,所以本目錄六批
**都沒有它**,讀的人必須自己補上那個資訊:

> **無 `pool_order` 欄的舊批次,其池順序為階段 3 之前的註冊表順序:**
>
> ```
> wolf, chess, fox, intruder, optimizer, builder, hunter
> ```

這就是上面 `--pool` 要逐字寫出的那份名單。對照一下階段 3 之後
`--pool no_imitation` 展開成的 key 排序 —— **內容相同、順序不同**:

| | 順序 |
| --- | --- |
| 舊批次（無 `pool_order` 欄，註冊表順序） | `wolf, chess, fox, intruder, optimizer, builder, hunter` |
| 階段 3 之後的 `no_imitation`（key 排序） | `builder, chess, fox, hunter, intruder, optimizer, wolf` |

所以「同一批名單、同一個種子」在兩種順序下會抽出不同的對手 —— 差別只在順序,不在
