# AGENTS.md — 單人 BLOKUS 開發守則

這個檔案是這個專案的長期記憶。**動工前先讀，改到規矩時一併更新。**
下面每一條都是踩過坑之後定下來的，不是偏好而已。

專案說明見 [README.md](README.md)（繁體中文，架構與公式的完整說明）。

---

## 一、專案宗旨

- 20x20 單人 Blokus：一位真人對上三個 AI，AI 每局換一種「人格」。
- 附一個全 AI 聯賽工具（`match.py`），用來回答「哪個人格比較強」。
- **AI 必須真的會下棋**，不是隨機走子。每一手都要能說出理由。
- 介面要清楚、耐看、對齊一致。排版整潔與算得一樣重要。

## 二、絕對不能違反的規矩

### 1. 視窗永遠是 16:9

`Layout.__init__` 先定 `H`，再由 `W = H * 16 / 9` 反推寬度。**不要**再出現獨立的
`W` 設定，也不要讓任何東西決定寬度。

手動拖曳視窗（`VIDEORESIZE`）會被**彈回**到 16:9。調整大小的唯一方式是 `+` / `-`
鍵（`bump_scale`），那會同時改變 `H` 並重算 `W`。

`tests/test_ui_smoke.py::test_window_is_locked_to_16_9_at_every_scale_and_zoom`
會在每個 scale × hand_zoom 組合檢查 `W / H == 16/9`。

### 2. 三欄式版面，欄與欄之間共用同一個 `MARGIN`

```
| 玩家資訊欄 |   棋盤   | 選方塊區(right-hand rack) |
   PANEL_W      board        HAND_W
```

- 垂直方向：`MARGIN` + 棋盤 + `MARGIN` + 按鈕 + `MARGIN` = `H`。
- 棋盤大小由高度反推（`board_px = H - 3*MARGIN - BTN_H`），所以 16:9 之下棋盤
  永遠是能放的最大值。
- 任何新的間距都直接用 `L.MARGIN`，**不要**自己寫 `int(round(N * s))` 的間距，
  否則對齊會開始漂移。

### 3. 選方塊區是右欄，一種大小一張卡

- 五張卡：1格 / 2格 / 3格 / 4格 / 5格。每張卡 = 上方標籤條 + 框住該組所有方塊的
  外框。
- **卡片會並排**：1～4 格的方塊數量少，卡片由左至右排滿一行再折行，不要退回成
  一列垂直堆疊（那會白白吃掉整個視窗高度）。每一行再整行置中。
- 欄很窄，組會自動折行。
- **方塊大小由「填滿右欄」反推**，不是固定的 scale 倍數：`_max_fitting_hand_cell()`
  找出整副手牌放得下的最大 cell，`hand_zoom` 只是它的一個比例（最高檔 = 填滿）。
  少了這一步，右欄會在下方留下一大片空白，跟旁邊填滿高度的棋盤比就不對稱。
- **寧可縮小，不可裁切**：cell 一定不超過放得下的最大值。
- **位置永遠固定**：`UI.hand_layout` 一律以**整副 21 塊手牌**計算幾何，
  `draw_hand` 只畫還在手上的方塊。用掉一塊只是留下空格，**其他方塊不得移動**
  ——重排會讓玩家看錯位，也容易點錯。

### 4. 玩家資訊欄依「出牌順序」排列

用 `game.turn_order` 迭代，不是 `range(4)`。座位編號是內部細節，玩家看不到；
第一列就是這一局先手。

### 5. 所有使用者可見文字集中在 `config.py` 的 `I` 字典

新增任何介面文字都要進 `I`，不要在 `ui.py` 裡寫死中文字串。`COLOR_LABELS`
與 `match.py` 的 CLI 輸出同樣維持繁體中文。

### 6. 程式碼註解一律英文；`README.md` / `AGENTS.md` 可用中文

註解與 docstring 用英文，文件用繁體中文。這是刻意的分工：註解是給讀程式的人看的。

## 三、必須記住的遊戲邏輯

### 分數 = 放不上去而留在手上的格數，愈少愈好

這是整個專案最重要的設計決定。因為分數是「餘格」，所以每個 AI 指標都刻意
**以「格」為單位**，權重之間可以直接比較：

| 目標               | 指標                             | 單位 |
| ------------------ | -------------------------------- | ---- |
| 少留格             | 剩餘格數                         | 格   |
| 保留延伸空間       | 落子後可放空格數                 | 格   |
| 不被封死           | 可用交點數                       | 個   |
| 圍出放得下大棋的地 | `pack_lost`（FFD 裝不下 的格數） | 格   |

### 規則過濾必須是「軟」的

`Brain.restrict` 篩不到東西時**必須退回原本的候選清單**。
做成硬過濾會讓候選清單變空 → `choose_move` 回傳 `None` → 呼叫端把玩家誤判成
「無棋可下」而自動跳過。這是最容易犯又最難查的 bug。

### 遊戲規則只在 `board.py` 實作一次

AI 評分與測試都走 `place_geometry` / `place_state`，兩邊不會各算各的。

## 四、開發時容易忘的技術細節

- 引擎模組不得 import `pygame`、`ai`、`records` 或 `ui`。
- 局面必須可序列化、可複製，複製不共享可變物件。
- `action_table.json` 的雜湊一旦發佈就不能更改，否則舊資料與舊模型作廢。
- 任何規則改動，必須同步更新引擎測試與交叉驗證。
- 行為保持不變的重構，必須附同種子逐手比對的結果。
- **棋盤是 400-bit 整數**（`empty_bits` / `owner_bits`）。合法性是幾個大整數的
  位移與求交，不是枚舉格子。`ai/formulas.py` 頂部有註解說明各個位元集合的含義。
- **`_score_move` 在 `chooser.choose_move` 裡被重寫了一次**（候選枚舉是熱路徑，
  那裡內嵌了算式省函式呼叫）。**改權重或評分式時兩處必須同步**，否則規則式人格
  的人格化會失效。`formulas._score_move` 的 docstring 有寫這件事。
- **規則式人格不做對手預判、不抽籤**（`uses_lookahead = False`、
  `mistake_rate = 0`）。預判用的是權重評分，量級與規則式目標函式完全不同，
  那一項會直接蓋掉規則排序。
- **權重式人格每局權重乘 0.7～1.3 隨機擾動**，否則排行榜會變成一組固定對局的
  重播。比較人格必須跑夠多局。
- **每局抽 4 個人格且互不相同**，所以每局都有幾個人格輪空。這是「所有人格互比」
  要的形狀。改 `personality_keys()` 的順序會改變既有種子下的對局結果 → 要可重現
  就把新的人格加在最後。
- **排行榜以人格為 key，不是座位**。`Game.setup_match` 檢查四個人格互不相同。
- **`records.json` / `settings.json` 執行時自動生成**，已在 `.gitignore`。
  載入與存檔都包在 `try` 裡：檔案損壞時當作沒紀錄，不讓遊戲開不起來。

## 五、新增一種 AI

1. 選一類：
   - **權重式**（只需要不同取捨傾向）：建 `ai/<name>.py`，定義 `KEY`、
     `PROFILE_SPEC`（7 個數字）與一個繼承 `WeightedBrain` 的類別。
   - **規則式**（有自己的目標函式）：建 `ai/<name>.py`，繼承 `Brain`，實作
     `context` / `restrict` / `rescore`，並設 `uses_lookahead = False`、
     `self.mistake_rate = 0.0`。
2. 在 `ai/registry.py` 登記（`WEIGHTED_SPECS` 或 `RULE_BRAIN_CLASSES`）。
3. 在 `ai/__init__.py` 匯出。
4. 在 `config.py` 的 `I` 加中文名與描述，並把 key 加進
   `config.PERSONALITY_ORDER`（`ui.py` 的 `PERSONA_ZH` 靠它產生）。
5. 寫測試。

分層原則：`formulas.py` 只回答「落子換算成數字」，人格模組只負責三個 method，
`chooser.py` 跑流水線但**不認識任何人格**。

## 六、測試規則

```bash
python3 -m pytest tests/ -q     # 159 項，約 2.5 分鐘
```

- **測試要從真實對局位置出發**（用 `Game.act` 走出來），不要把棋塊硬放上去：
  角對角規則意味著 owner 0 必須先開在自己的角上，否則 `reach` 對所有候選都是錯的。
- **版面測試要 pin 幾何性質，不要 pin 魔法數字**。例如手牌帶高度取決於折行，
  就斷言「五張卡放得下視窗高度」，不要寫死某個像素值。改了裝飾就會誤報。
- `test_ui_smoke.py` 會用 spy 攔截 `UI.label` 檢查文字有沒有超出面板；
  **`label()` 的簽章若加了參數，四個 spy 都必須同步更新**，否則測試會炸在
  `TypeError` 上。
- 版面改動後務必截圖檢視（`SDL_VIDEODRIVER=dummy` 跑 headless 存 PNG），
  測試只驗證幾何，不會告訴你「看起來亂」。

## 七、其他慣例

- Python 3，無型別註解，無外部相依（除 `pygame`）。
- 模組頂部有一句話 docstring 說明「這層只回答什麼問題」。
- 註解解釋**為什麼**，不重述程式在做什麼。
- 已知近似（例如 `fillable_closure` 只是上界）要寫在註解裡當作已知代價。
- 提交前跑完整測試；`.gitignore` 已排除 `__pycache__`、`.pytest_cache`、
  `records.json`、`settings.json`。
