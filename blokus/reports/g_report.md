### 吞吐粗測（量測非結果）

模型：6 個殘差塊、64 通道、輸入 14 通道，每塊兩層 3×3 卷積 + BatchNorm +
ReLU；policy 頭 1×1 卷積輸出 91 通道，value 頭 1×1 卷積輸出 4 通道。
**參數 458,271。用完即丟。**

推論（`fp16` autocast + `torch.inference_mode()`，預熱 10 次後取 50 次平均）：

| batch | 平均 ms | 中位數 ms | 最小 ms | 最大 ms | 每秒局面數 |
| --- | --- | --- | --- | --- | --- |
| 64 | 3.5256 | 3.5231 | 3.4538 | 3.7011 | 363.1 |
| 256 | 4.1796 | 4.2563 | 4.0239 | 4.5937 | 1,225.0 |
| 1024 | 26.8748 | 26.9175 | 26.2594 | 28.0824 | 762.1 |

batch=1024 的每秒局面數**低於** batch=256（762 vs 1,225）。這不是量測誤差：
20×20 的特徵很小，batch 1024 時 policy 頭輸出 1024×91×20×20 = 37,326,080 個元素，
fp16 就是 71.1 MB；batch 256 時只有 17.8 MB。**如果要吞吐，batch 256 是這張卡上
這個模型的甜蜜點**；再往上只會更慢。

一次「前向 + 反向 + 優化器步」，batch = 256、AdamW lr=1e-4、
MSE 對隨機 `(91, 20, 20)` 目標（代替真正的 policy 目標函數）：

| 項目 | 值 |
| --- | --- |
| 平均 | 20.6751 ms |
| 中位數 | 21.3286 ms |
| 最小 / 最大 | 17.6988 / 22.8355 ms |
| 每秒局面數 | 247.6 |
| 最後一次 loss | 0.9991368055343628 |
| `max_memory_allocated` | 642,076,672 bytes = 0.598 GiB |
| `max_memory_reserved` | 801,112,064 bytes = 0.764 GiB |

峰值顯存 0.6 GiB / 15.5 GiB，所以顯存不是限制；瓶頸是 kernel 啟動與這張卡的
運算量，不是容量。

91 個方向 × 400 個 base = **36,400 個槽位**，其中只有 **30,433 個是真實落點**。
索引空間是真實動作的稀疏超集，這是為了好讓 policy 輸出一個固定的軸。

**旋轉等變性是這一節最重要的一項測試。** `rotate_state` 是引擎自己的順時針一步，
它連棋子朝向、base 與玩家編號一起轉。如果合法步集合沒有跟著棋盤轉，
那麼「行動者視角」和「動作索引」就在講兩個不同的座標系，模型會被要求下一步
不存在的棋。

### 兩點實作說明

**旋轉從不另寫公式。** `LUT_ROT` 是把 `engine.rotate_move` 連套 k 次建出來的，
所以 repo 裡只有一個旋轉定義，就是規則用的那個。非正方形外框的棋子正是
手寫公式會忘記移動 base 的地方。

**`legal_indices` 不經過 Python 的 `set`。** 直接從引擎的整數 mask 做
一次位元組解包 + 表查換：

| 量測（量測非結果，29,580 個局面） | 平均 ms |
| --- | --- |
| `engine.legal_move_mask` | 0.5059 |
| `rl.actions.legal_indices` | 0.5549 |
| `rl.actions.legal_mask_view` | 0.5978 |
| `engine.legal_moves`（回傳 frozenset） | 0.6571 |

`legal_indices` 比 `legal_moves` 快 16%，代價只有 0.05 ms；比
`legal_move_mask` 慢 0.05 ms 是解包本身的成本。這個差距很小，所以選擇的
依據不是速度而是**不做 set**：迭代順序依賴 hash seed，
而採樣動作必須與 `PYTHONHASHSEED` 無關。

## G2 特徵（`rl/features.py`）

14 個通道，12 個標量，4 組手牌，全部是**行動者視角**。
兩個只在旋轉上不同的局面必須產生完全相同的陣列 —— 這是之後能做旋轉增強的前提。

前 7 個通道與 `engine.to_plane` **逐位元相同**，這是正確性的 oracle，
而且是對照引擎本身，不是對照一份抄寫。

### 通道表

| 序號 | 名稱 | 內容 |
| --- | --- | --- |
| 0 | `me` | 我方石頭 |
| 1 | `next` | 下家石頭 |
| 2 | `opposite` | 對家石頭 |
| 3 | `previous` | 上家石頭 |
| 4 | `my_need` | `need & ~avoid & empty`，與 to_plane 相同 |
| 5 | `my_avoid` | `avoid`，與 to_plane 相同 |
| 6 | `empty` | 空格，與 to_plane 相同 |
| 7 | `next_need` | 下家的 `need & ~avoid & empty` |
| 8 | `opposite_need` | 對家的同上 |
| 9 | `previous_need` | 上家的同上 |
| 10 | `start_me` | 我尚未開局時，起始角格為 1；否則全 0 |
| 11 | `start_next` | 同上（下家） |
| 12 | `start_opposite` | 同上（對家） |
| 13 | `start_previous` | 同上（上家） |

座標旋轉方向**沒有假設**，而是用測試確立：`np.rot90(a, -1)` 是順時針。
測試顯式建立 `(x, y) → (B - 1 - y, x)` 的置換再比對，
因為方向弄反會產生仍然自洽、但整體錯誤的陣列。

**為什麼需要 7-9 與 10-13：** 7 是引擎的七通道，說得出一個局面但說不出
怎麼走。對手的接觸規則是他們石頭旁邊可以碰、可以站、不能站的格子；
沒有它，模型分不清「 inviting」和「有毒」的格子。而尚未開局者的
`need_avoid` 回傳空集合（引擎的預期行為），所以起始角格必須另外給。

### 標量（長度 12）與手牌

| 序號 | 名稱 | 內容 |
| --- | --- | --- |
| 0-3 | `stuck_me`, `stuck_next`, `stuck_opposite`, `stuck_previous` | 0 或 1，取自 `state.stuck`，依座位 |
| 4-7 | `remaining_*` | 餘格除以 89 |
| 8-11 | `opened_*` | 該玩家石頭是否非空 |

`hands` 形狀 `(4, 21)` `float32`，與 `engine.hand_vectors` 逐位元相同。

### 兩種做法的耗時對照（量測非結果）

設計上 plan3 給了兩個選項：只用一次 `normalize`，或完全不用 `normalize`
而在真實座標算完遮罩後用 `np.rot90`。**本專案選了後者**，理由是量測結果。

100 局的全部局面（排除 mask == 0 的決策點），前一 50 個預熱不計：

| 階段 | n | `featurize` 平均 ms | `featurize_via_normalize` 平均 ms | `to_plane` + `hand_vectors` 平均 ms | 對舊路徑加速 |
| --- | --- | --- | --- | --- | --- |
| 開局（n < 16） | 1,600 | 0.1227 | 0.1687 | 0.2501 | 2.04× |
| 中盤（16 ≤ n < 48） | 3,200 | 0.1163 | 0.2597 | 0.4360 | 3.75× |
| 殘局（n ≥ 48） | 1,116 | 0.1072 | 0.3108 | 0.5493 | 5.13× |
| **全部** | **5,916** | **0.1185** | **0.2919** | **0.4142** | **3.50×** |

三個數字說三件事：

1. **`featurize` 比引擎的 `to_plane` + `hand_vectors` 快 3.50 倍**（全部局面）。
2. **加速比隨進度增長**：開局只快 2.04 倍，殘局快 5.13 倍。因為
   `engine.normalize` 的成本正比於旋轉次數與棋盤大小，而 `to_plane` 的遮罩
   工作正比於棋子數（殘局少得多）。`np.rot90` 的成本只正比於資料量，
   不隨階段變化 —— 這就是 `featurize` 三個階段耗時幾乎持平
   （0.1227 / 0.1163 / 0.1072 ms）的原因。
3. **不用 `normalize` 比只用一次 `normalize` 快 2.46 倍**（0.1185 vs 0.2919 ms）。
   F′ 量到 `to_plane` 有 65% 的時間花在 `normalize`，而這裡把那份成本完全拿掉了。

`featurize_via_normalize` 仍保留，因為它是 oracle：測試斷言兩者三項輸出全部相同，
所以這個加速是有論證的性能選擇，不是對規則的第二種意見。

批次（量測非結果）：

| batch | 總耗時 ms | 每局面 ms |
| --- | --- | --- |
| 1 | 0.0793 | 0.0793 |
| 32 | 3.8564 | 0.1205 |
| 256 | 29.9821 | 0.1171 |

**批次在這裡沒有好處**：`featurize_batch` 的主要成本是每個局面的 Python 迴圈
（座位重排、標量、手牌），不是 numpy 計算，所以把 256 個局面疊起來不會比
逐個算快。要批次真正划算，必須先把那段 Python 迴圈向量化 —— 本階段不做。

## G3 環境包裝（`rl/env.py`）

`BlokusEnv` 隱藏兩個引擎內部的陷阱。

**陷阱一：`state.to_move` 不是保證。** `_advance` 依 owner id 0→3 掃描並在
第一個還能走的玩家處 break，所以被交棒的那位可能沒有合法步。F′ 實測這是
5.7% 的決策點、84% 的局。`step` 因此在套用動作後自動 pass 到有人能走為止，
對外只給一個有用的契約：**`done` 為 False 時，`legal_indices()` 一定非空。**

**陷阱二：並列。** `Game.standings` 用座位編號破壞並列，確定但有偏，
所以這裡不用它。名次採競爭排名並列者平分所跨名次，與
`tools.benchmark.average_ranks` 同一規則。效用 = `(4 - 平均名次) / 3`，
第 1 名 1.0、第 4 名 0.0，四人總和恆為 2.0。

## G4 試產資料（`rl/collect.py`）

老師是 **optimizer** 人格。選它的理由高於其他：F′ 量到它在同種子兩次呼叫下
0 / 500 次不同，也就是它的 top-1 動作是位置的函數。學一個確定性的標籤有東西可以
學到；學一個四分之一的時候會換答案的人格，等於要求猜。

但那個確定性正是問題。四個 optimizer 互打，每一局一模一樣，資料只有一條路。
所以每一局加入兩種多樣性，都由局種子決定：

- **隨機開局前綴**：從 `{0,2,4,6,8,10,12}` 抽一個長度，前 R 個真實手下隨機合法步，
  但**照樣取標籤** —— 局面是真實的，只是到達它的動作不是被選的。
- **座位控制者**：每座位獨立抽，optimizer 50%、wolf/chess/fox 各 12.5%、
  intruder/builder 各 6.25%；若四座都沒抽到 optimizer 就重抽整局設定。

## G5 normalize 查證

plan3 的疑點是對的，而且比預期更徹底。

`engine.normalize` 把行動者放在索引 0（`seat_of[0] == state.to_move`，
這一點已驗證），但開局規則讀 `OWNER_CORNER[owner]`，而 owner 0 的角格是
`(19, 19)`，即右下角。所以對 view 呼叫 `legal_move_mask`，若行動者尚未開局，
會把「owner 0 的右下角」當起始角格。

### A / B 比較結果

A = `real_to_view(legal_indices(s), p)` 的集合，
B = 對 `engine.normalize(s)` 的 view 直接呼叫引擎得到的集合。兩者都在行動者視角座標下。

| 情境 | 局面數 | 相等 | 不相等 | 不等比例 |
| --- | --- | --- | --- | --- |
| **行動者尚未開局** | 200 | **0** | **200** | **1.0000** |
| 行動者已開局 | 200 | 200 | 0 | 0.0000 |

按行動者 owner 分組（尚未開局的情境，每位各 50 個局面）：

| 行動者 owner | 局面數 | 相等 | 不相等 |
| --- | --- | --- | --- |
| 0 | 50 | 0 | **50** |
| 1 | 50 | 0 | **50** |
| 2 | 50 | 0 | **50** |
| 3 | 50 | 0 | **50** |

已開局的情境：owner 0 有 51 個局面全等、1 有 54、2 有 48、3 有 47，**全部相等**。

### 不相等時的樣子

抽樣種子 0、第一位行動者 owner 1：

| 項目 | 值 |
| --- | --- |
| 真實座標合法步數 | 58 |
| view 座標合法步數 | 58 |
| 只在 A（正確）中的 | 58 |
| 只在 B 中的 | 58 |
| 交集 | **0** |

**兩邊都是 58 個，但交集為零。** 兩個集合完全不重疊，不是「多算或少算幾個」，
而是算的是完全不同的角格。

直接檢查兩邊蓋到哪些角格（真實座標下手動建構一個 `to_move = 2` 的空盤局面，
owner 2 的角格是 `(19, 0)`）：

| 集合 | 蓋到的角格 |
| --- | --- |
| A（正確） | `{(0, 0)}` —— 視角座標下自己的起始角（左上） |
| B（view 上直接算） | `{(19, 19)}` —— owner 0 的角格（右下） |

**懷疑完全成立，而且每一位行動者都成立，沒有任何角落是例外。**
已開局的玩家不受影響，這也與預期一致。

`to_plane` 本身沒有踩到這個坑，因為開局時 `need_avoid` 回傳空集合。

### 為什麼這不影響本專案的程式

**`rl/` 的所有程式一律遵守：合法步只在真實座標的 `State` 上計算，
再用 `LUT_ROT` 轉到視角座標。** 沒有任何地方對 normalize 的 view 呼叫
`legal_move_mask` 或 `apply_move`。`rl/actions.py`、`rl/env.py`、`rl/collect.py`
全部走真實座標。這也是 G1 的旋轉等變性測試存在的理由：那個測試正是把
「視角座標的合法步」與「旋轉後的真實座標合法步」對照，
如果有人將來改成在 view 上算，這個測試會立刻失敗。

**沒有修改 `engine.py`。**

## 異常與未預期發現

1. **`normalize` 的開局 bug 影響每一位行動者，不只部分角落。**
   200 個未開局局面全部不相等，owner 0/1/2/3 各 50 個全錯。
   A 與 B 的交集是 **0** —— 不是數量偏差，是完全不同的角格。
   任何在 view 上算開局合法性的人，得到的是一個看起來合理（58 個步）
   但每一個都錯的答案。

2. **舊速度路徑的成本隨進度增長，新的不變。**
   `to_plane` + `hand_vectors` 從開局 0.2501 ms 漲到殘局 0.5493 ms（+120%），
   `featurize` 從 0.1227 ms 微降到 0.1072 ms（−13%）。加速比因此從 2.04× 變 5.13×。
   這意味著舊路徑的瓶頸會隨對局進行而惡化，任何依賴它的批次流程都會在中後盤變慢。

3. **`featurize_batch` 在這個尺寸沒有好處。**
   batch 1 是 0.0793 ms/局面，batch 256 是 0.1171 ms/局面 —— **批量化反而慢 48%**。
   原因是主要成本在每個局面的 Python 迴圈（座位重排、12 個標量、84 個手牌位），
   不是 numpy。要批次划算必須先把那段迴圈向量化。

4. **GPU 的 batch 甜蜜點是 256，不是 1024。**
   推論每秒局面數：batch 64 = 363.1、batch 256 = 1,225.0、batch 1024 = 762.1。
   batch 1024 比 256 **慢 38%**，因為 policy 頭在 1024 時輸出 71.1 MB fp16
   （batch 256 只有 17.8 MB），記憶體流量成為瓶頸。這與直覺「批次越大越快」相反。

5. **trial run 的資料量比預期少約 40%。**
   2,200 局只產生 86,788 個樣本（39.4491/局），因為樣本恰好等於
   「老師座位上的真實決策點數」：平均 2.16 個老師座位 × 68.37 手 ÷ 4 座位 ≈ 36.5，
   再加上終局輪轉偏向老師座位，實測 39.45。
   若要 100 萬樣本量級，按這個比率需要約 25,349 局，
   以 12 進程 82.9 秒 / 2,200 局推算約 15.9 分鐘、磁碟約 66 MiB。

6. **optimizer 座位的實際佔比 0.5402 高於設計的 0.5000。**
   這是「沒有老師就重抽整局」的必然結果，不是抽籤偏差。
   重抽率是 1 - 0.5⁴ = 6.25% 的局，每次重抽平均再帶來 2 個老師座位。
   已在報告中說明，因為它會影響任何依賴座位數分布的統計。

7. **`in_prefix` 比例 8.312% 只有「R 全部被標記」理論值 15.23% 的一半。**
   前綴平均 6.007 個真實手、樣本平均 39.4491 個，若前綴手全部被標記應是 0.1523。
   實測 0.0833，因為 R 個手分給 4 個座位時只有約 2.16 個座位是老師，
   而 R 個手未必輪到每一位老師。**這個比例應該與前綴長度成正比**：
   若前綴長度改了而它沒跟著變，就是 bug。300 局抽樣得 0.08343，與全量一致。

8. **`n_candidates` 與 `n_legal` 在全部 86,788 筆樣本中逐筆相等。**
   這是正確的（optimizer 的 `restrict` 是軟篩選，不丟棄候選），
   但它代表這個欄位對老師而言是冗餘的。若換一個會硬篩選的人格，兩者才會分開。

9. **`legal_indices` 對 `legal_moves` 的加速只有 16%。**
   F′ 說 `legal_moves` 比 `legal_move_mask` 慢 25%，而我原本預期繞過 set 會更顯著。
   實測 0.5549 vs 0.6571 ms。選它的理由已如實記錄：**不是速度，是避免
   迭代順序依賴 `PYTHONHASHSEED`**。

10. **`rl/collect.py` 的第一次執行就因 `KeyError: 'path'` 失敗。**
    分片改為依樣本上限切分後，`results` 的形狀從「一個 worker 一個
    `path`」變成「一個 worker 若干個 `shards`」，`main()` 沒跟著改。
    已修正，並且 `main()` 現在從**寫出的分片**讀回資料做統計，
    而不是重用 worker 記憶體裡的 rows —— 這讓統計變成對「實際寫了什麼」的陳述。

11. **`collect` 的 `stack()` 原本會把兩個 payoff 欄位升成 float64。**
    `np.stack` 對 Python float 的清單會推導出 `float64`，而宣告的規格是
    `float32`。已改為顯式 cast，否則每個分片的兩個 payoff 欄位會默默變成兩倍大小。

12. **`dilate` 與 `dilate_diag` 的交集非空。**
    這在寫 G2 的 `*_need` 通道測試時才發現：兩個相鄰的石頭會讓某個格子
    對其中一個是對角鄰接、對另一個是邊鄰接，於是它同時落在 `need` 與 `avoid` 裡。
    所以 `need & ~avoid` 不是防禦性程式碼，它真的會刪掉東西 —— 測試裡
    有一個刻意構造這種局面的案例。

**沒有修正任何既有檔案。**
